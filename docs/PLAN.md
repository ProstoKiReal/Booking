# План имплементации

- [ ]

## Шаг 0

Contract-first. Прежде чем писать код — опиши события и API-контракты между сервисами (хотя бы в markdown/AsyncAPI): EventPublished, SeatReserved, OrderCreated, PaymentCompleted и т.д. Это заставит сразу продумать границы контекстов, а не изобретать их на ходу.

- [ ]

## Шаг 1

Catalog Service — самый простой, без саги и локов.
Поднимаешь Postgres + FastAPI, делаешь DDD-слои (domain / application / infrastructure / presentation), CRUD для Event/Venue/SeatMap. Цель — обкатать сам скелет: как выглядит агрегат, репозиторий, доменные события, как устроен outbox-паттерн (запись в таблицу outbox в той же транзакции). Здесь тебе ещё не нужен брокер — можно временно логировать outbox-события в консоль или сразу написать relay-воркер (это уже часть паттерна, лучше сделать сразу).

- [ ]

## Шаг 2

Подними инфраструктуру вокруг: Kafka/RabbitMQ + Keycloak.
Прикрути Keycloak как issuer, сделай middleware валидации JWT в Catalog Service. Подними брокер, доведи outbox-relay из Catalog Service до реальной публикации сообщений.

- [ ]

## Шаг 3

Booking Service (Go) — ядро конкурентности.
Здесь пишешь резервацию места с блокировкой (сначала просто SELECT FOR UPDATE, потом можно добавить optimistic-версию как альтернативную ветку/фичефлаг для сравнения). Добавляешь TTL-воркер на очистку просроченных holds. Подписываешься на EventPublished/SeatMapUpdated из Catalog, строишь свою локальную read-модель (CQRS-элемент).

- [ ]

## Шаг 4

Order & Payment Service — самое сложное, поэтому последнее.
Сначала — просто happy path без саги (создал заказ → вызвал Booking → вызвал mock-Payment → confirm). Потом добавляешь явную state machine саги, компенсации, идемпотентность. Это тот момент, где боль от отсутствия правильного фундамента в Booking/Catalog вылезет наружу — но ты уже успеешь их обкатать раньше.

- [ ]

## Шаг 5

Фронт на Vue — в последнюю очередь или параллельно с шагом 3, когда есть хотя бы Catalog + Booking, чтобы был смысл рисовать схему зала.

- [ ]

## Шаг 6

Observability и нагрузочное тестирование — в конце, но не забудь: именно нагрузочный тест на конкурентные брони одного места — это то, что визуально докажет, что твои локи работают. Без этого «прод-ready» момент останется голословным.
